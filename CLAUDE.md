# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LocalDevEngine (internal package name `dev_orchestrator`) is a "Stacked Intelligence Architecture": a local, Ollama-backed orchestrator that routes a coding task through a pipeline of specialized models instead of using one model for everything, to optimize VRAM usage and reasoning quality per stage.

See [README_DOCUMENTATION.md](README_DOCUMENTATION.md) for the original model-hierarchy table. The doc is still explicitly partial ("Part 1 complete") and its model names/tags are a simplified sketch — `config/settings.yaml` is authoritative for real Ollama tags when the two disagree (see Config below).

## Current state: runnable, verified end-to-end

`python main.py ask "<query>"` and `python main.py chat` work against a local Ollama server. The full pipeline (Router → RAG → Manager → Architect↔QA design gate → Implementer↔QA implementation check) has been run live to completion multiple times, including a full smoke test that closed with `Implementation check attempt 3: APPROVED`.

What got this from scaffold to runnable, across 11 commits on `main` (`git log --oneline`):

- `memory/local_memory.py`'s `self.metadata`/`embedding.size` bugs are gone — the store was rewritten with atomic `.npy`+`.json` writes (temp file + `os.replace`), shape/dimension validation on load, float32, and normalized vectors so `search()`'s `np.dot` really is cosine similarity.

- **No lint/build tooling configured.**
- **QA stages never stream.** `on_chunk` is wired for every model-output stage the user actually reads (fast path, design plan/revision, implementation) but deliberately not for `qa_auditor` calls, since only the parsed VERDICT/FEEDBACK is surfaced, never the raw QA response text.

- **Deterministic schema grounding is built** (`context/schema/*`, opt-in via `--schema-file`) per [docs/plan-schema-grounding.md](docs/plan-schema-grounding.md): a caller-supplied DB schema snapshot is rendered as an authoritative, unscored block ahead of RAG, plus a model-free post-implementation identifier check. ## Architecture

**Design patterns**: `models/base.py` defines `BaseModel` as an ABC (Strategy pattern) so providers other than Ollama could be added later, now including a `generate_stream()` abstract method alongside `generate()`. `models/factory.py`'s `ModelFactory` (Factory pattern) reads `config/settings.yaml` and builds a role-specific `OllamaModel` instance on demand via `create_role_model(role_name)`. `memory/base.py` similarly defines `BaseMemory` as an ABC so the local NumPy vector store (`memory/local_memory.py`) could be swapped for a real vector DB; its `add_text` signature now matches the real implementation (`text, metadata, embedding`).

**Request flow** (`core/orchestrator.py: Orchestrator.run_complex_task`, which wraps the actual pipeline logic in `_run_pipeline_body`):
1. **Router** (`_get_router_decision`) classifies the query into `SIMPLE_TASK` / `COMPLEX_ARCHITECTURE` / `CODING_REQUEST` / `ERROR_REACTION`. `SIMPLE_TASK` and `ERROR_REACTION` take a **fast path**: a single Manager call answers directly, skipping RAG/schema/Architect/Implementer/QA entirely (`outcome.schema_grounding`/`outcome.context_budget` are `{"ran": false}` even if a snapshot was supplied — the fast path builds no context at all).
2. For the full pipeline, three context sources are gathered and then merged under one shared budget:
   - **Schema block** (`_build_schema_context`, only if the caller passed `--schema-file`): selects a lexical subset of the caller's `SchemaSnapshot` plus one hop of FK closure (`context/schema/selection.py`), renders it as a labeled, unscored, authoritative block (`context/schema/render.py`). Synchronous and model-free — never calls Ollama, never opens a DB connection. See "Schema grounding" below.
   - **RAG** (`_build_rag_context`) embeds the query via `EmbeddingService` (`/api/embed`, `truncate:false`), retrieves top-k chunks from `LocalVectorMemory` (cosine similarity), caps chunks per source, attributes each with its file path + score. Returns `(pieces, stats)` **without truncating** — that used to happen here, capping only the chunks while everything appended after them grew unbounded (see next bullet).
   - **`_assemble_context`** is the single place `retrieval.max_context_chars` is enforced, over every block that reaches a prompt: schema block, Manager outline, macro-loop prior report, then RAG chunks, in that fixed priority order — RAG is the only block allowed to drop pieces to fit, and does so first. Returns `(context, budget_stats)`; `budget_stats` feeds `outcome.context_budget` (`schema_chars`/`breakdown_chars`/`rag_chars`/`rag_pieces_included`/`rag_pieces_dropped`/`used_chars`/`over_budget`). Called twice per full-pipeline run — once (with a reserved gap) before the Manager writes its outline, once for real once the outline exists — so the Manager and the Architect never see different chunk sets.
3. **Manager** (`get_manager_breakdown_template`) turns the goal + assembled context into a short step outline, which then goes into the final `_assemble_context` call above.
4. **Architect** produces a plan via `get_architect_thinking_template`, which now forces exactly four `## <Name>` sections (`PromptRegistry.SECTION_NAMES`: Data Model, API/Interface, Error Handling, Dependencies/Integration). `_split_plan_sections()` parses them back out.
   - If parsing succeeds: a **sectioned design gate** reviews and — if rejected — regenerates *one section at a time* (`get_section_review_template`/`get_section_revision_template`), each pass seeing the full plan for cross-section consistency. Verified live to regenerate a rejected section in ~29-73s vs. 50-150s for a full-plan regen.
   - If the model doesn't follow the format (returns `None`): falls back unchanged to the original **monolithic design gate** (`get_design_review_template`/`get_architect_revision_template`), looped up to `max_qa_iterations`.
   - Either branch's approved/attempts-per-section result feeds `outcome.design_gate` in the receipt.
5. **Implementer** (`get_implementer_task_template`, now taking an optional `output_contract` param) produces code from the approved plan + context, then a post-implementation QA check (`get_qa_review_template`, also `output_contract`-aware) can send it back through an Architect revision → re-implementation loop, also up to `max_qa_iterations`. When `output_contract="fenix-tagged-file"`, both the Implementer's prompt and the QA's verdict criteria change — see "Output contracts" below.
6. If `pipeline.closing_report` is on, the Manager closing report runs (unchanged from before).
7. **Returns a receipt** (built by `core/receipt.py: build_receipt()`), not a bare result dict — see "The receipt" below. The legacy top-level keys (`plan`, `implementation`, `fast_path`, `qa_approved`, `qa_feedback`, `breakdown`, `closing_report`, `deviation`, `request_id`, `trace`, `macro_iteration`) are still present at the top level for backward compatibility with `main.py`'s internal consumers.

**The receipt** (`core/receipt.py`, `SCHEMA_VERSION` **1.1**, `docs/plan-receipt-interface-callers.md`): every `run_complex_task` call returns `{schema_version, request_id, status, query, query_sha256, started_at, finished_at, duration_ms, macro_iteration, outcome, config_fingerprint, artifacts, trace, error}` plus the legacy keys above. `status` is `"completed"`, `"failed"` (a `ModelCallError` was caught mid-run), or `"timeout"` (see below) — in the latter two cases `trace` is whatever ran before the failure/cutoff, and `plan`/`implementation`/etc. are `None`. `outcome` carries the per-stage signals a non-human caller needs — `rag`, `schema_grounding`, `context_budget`, `design_gate`, `implementation_check`, `closing_report` — each with an explicit `"ran": true|false` so "didn't run" and "ran and found nothing" are never confused. `config_fingerprint` snapshots the model tags/iteration caps/retrieval budget actually used for that run, built fresh from `self.config` every time — never staleable — plus a `request` sub-block (`output_contract`, `schema_grounding`, `schema_tables`) that records the per-request params `self.config` alone can't see (the `output_contract`-not-in-fingerprint gap flagged during schema-grounding work — `docs/plan-schema-grounding.md` §5.1, Fase 0 — fixed once for both params). The whole thing is intentionally **not** an independent attestation: it's produced by the same code being audited, so it can only ever lower a caller's confidence (by revealing it did less than expected), never prove correctness on its own — see `docs/handoff-fenix-parte-b.md` for how a caller is expected to treat it. **Exception:** `outcome.schema_grounding.identifier_check` is model-free and reproducible — a caller can recompute it independently from `(implementation, snapshot)` and verify it matches, which is more than any other field in the receipt can claim.

**Timeout / failure handling**: `run_complex_task` wraps `_run_pipeline_body` in `asyncio.wait_for(..., timeout=pipeline.max_run_seconds)` (config, default 1500s, `null`/`0` disables) and a `try/except ModelCallError`. Either produces a full receipt with `status="timeout"`/`"failed"` and a populated `error: {stage, role, model, message}` instead of an unhandled exception or a killed process losing all trace data — this is the one thing a caller killing the process on its own wall-clock cap would otherwise destroy.

**Output contracts** (`prompts/specialized_prompts.py: PromptRegistry.OUTPUT_CONTRACTS`): an opt-in `output_contract` string threaded through `run_complex_task` → Implementer/QA prompts. Currently only `"fenix-tagged-file"`, whose grammar (`STATUS`/`SUMMARY`/`=== FILE START ===`/`PATH`/`ACTION`/`--- CONTENT ---`/`=== FILE END ===`) is copied verbatim from fenix's own `delegate-low-rri.py: build_payload()` system prompt, so its existing parser accepts the output unmodified. When active, the implementation-check QA is explicitly instructed to reject grammar violations as `NEEDS_REVISION` regardless of whether the underlying code is correct — mitigates (but, being self-reported, does not eliminate) the risk of `qa_approved: true` hiding output the caller's parser can't actually consume. CLI: `python main.py ask --output-contract fenix-tagged-file "<query>"`.

**Schema grounding** (`context/schema/*`, opt-in via `--schema-file`, `docs/plan-schema-grounding.md`): a per-request IR of the caller's real DB schema — `SchemaProvider` ABC (`context/schema/base.py`, mirroring `models/base.py`/`memory/base.py`), currently one `SnapshotFileProvider` that loads and normalizes caller-exported JSON/YAML (`context/schema/snapshot.py`). Rendered as a block labeled "DETERMINISTIC SCHEMA (AUTHORITATIVE)" that carries no relevance score and is told to win over retrieved prose where they disagree (`context/schema/render.py`) — unlike RAG chunks, which are candidates, this is asserted. Selection is lexical, convention-agnostic (`snake_case`/`CamelCase`/plurals all collapse to the same candidate), and **fails toward including** a table rather than omitting one, since an omitted table is exactly what the model would invent. After the Implementer runs, `check_identifiers()` (`context/schema/identifiers.py`) flags table/column references in the output that aren't in the snapshot — reported in `outcome.schema_grounding.identifier_check`, but does **not** gate the QA verdict (that's Fase 4, gated behind the empirical check below). The engine never opens a database connection or holds credentials; the snapshot is exported and supplied entirely by the caller. **Still pending, and blocking before anything else is added to this layer:** an empirical gate that has never run the full pipeline against a case designed to make the model misname a column without the schema block — `docs/plan-schema-grounding.md` §5.2 has the pass/fail criterion, fixed before measuring. CLI: `python main.py ask --schema-file schema.json "<query>"`.

**Streaming**: every stage whose raw output the user actually sees (fast path, design plan/revision — sectioned, monolithic, and post-implementation — and implementation) accepts an `on_chunk(text, stage, attempt)` callback threaded through `_call_model` → `model.generate_stream()` (NDJSON over Ollama's `stream:true`). `main.py`'s `_make_stage_printer()` uses this to print colored stage headers (keyed by `(stage, attempt)` since a stage like `design_revision` can run multiple times) and stream text live instead of waiting for the full response.

**Ingestion** (`core/ingestor.py: DataIngestor.ingest_directory` + `core/chunking.py: chunk_file`): walks a directory (exact-name dir pruning, not substring — `.git` no longer matches `mi.github/`), sorted for reproducible ordering. Each matching file is split by structure (`.py` on `def`/`class`/`@` at column 0, `.go` on `func`/`type`/`package` at column 0, `.md` on headers, else paragraph breaks) into chunks capped at `max_chunk_chars`, with a two-stage fallback (line windows → character windows) for oversized units. `.go` is in `ingestion.extensions` by default now (added for the fenix integration — a Go codebase — see below). Chunks are embedded in batches and written via `LocalVectorMemory.replace_source` — embed-then-replace, not remove-then-embed, so a mid-ingest crash can't leave a source's old chunks deleted with nothing to replace them. Oversized embed batches bisect to find the offending chunk. Returns an `IngestSummary` with indexed/skipped/failed counts and per-failure reasons — no more silently-inflated file counts.

**Config** (`config/settings.yaml`): single source of truth for the Ollama model tag per role, retrieval budget, schema-grounding knobs, and storage paths. Current mapping: `router`→`phi3:mini`, `manager`→`gemma4:26b-a4b-it-qat`, `architect`→`qwen3.6:35b-a3b` (`think: false`), `implementer`→`qwen3.6:35b-a3b` (`think: false`), `qa_auditor`→`gemma4:26b-a4b-it-qat` (same tag as manager — an MoE swap chosen because it respects the VERDICT/FEEDBACK format far faster than the dense model it replaced; see inline comments in the YAML for the measured numbers behind each model choice). These differ from the README's simplified names (e.g. `qwen3.6:27b`, `gemma4:26b-it`), trust `settings.yaml`. `pipeline.max_run_seconds` (default 1500) caps a whole `run_complex_task` call, independent of `request_timeout_seconds` (which is per-HTTP-call). `retrieval.max_context_chars` (default 6000, raised from 3000) is now the real ceiling on the entire assembled context (see Request flow above) — the schema block, breakdown, and prior report all count against it, not just RAG chunks. `schema_grounding:` (`max_tables: 12`, `max_chars: 4000`, `fk_expansion_depth: 1`, `include_all_if_no_match: true`, `identifier_check: true`) tunes the layer described above; all of it is inert unless a request passes `--schema-file`. Every role may also set an optional `keep_alive` (duration string, seconds, `0`, or a negative number; unset = Ollama's own ~5min default) that's threaded straight into `OllamaModel`'s request payload — no role sets it today, this only makes the key available. See [docs/plan-model-lifecycle-keep-alive.md](docs/plan-model-lifecycle-keep-alive.md).

Ollama calls default to `http://localhost:11434/api`, overridable via the `LDE_OLLAMA_HOST` env var (read once in `Orchestrator.__init__`, threaded through `ModelFactory`/`EmbeddingService`/`OllamaModel`) — added so an external caller running its own Ollama instance (e.g. fenix) doesn't have to edit `settings.yaml`. Ollama's single-slot (`-np 1`) config means role-swapping between models forces an unload+reload, which is a real latency factor independent of any of the above. `OllamaModel.unload()` is now a real primitive (a `keep_alive: 0` generate call) rather than a no-op, and `keep_alive` is configurable per role, but nothing in the orchestrator calls `unload()` and no role sets `keep_alive` by default — this swap-latency cost is unchanged until a caller is wired in (deliberately deferred; see [docs/plan-model-lifecycle-keep-alive.md](docs/plan-model-lifecycle-keep-alive.md)).

## Interfacing with a non-human caller (fenix)

`python main.py ask --json [--out FILE] [--quiet] [--output-contract fenix-tagged-file] [--schema-file FILE] [--input-file FILE | "<query>"]` — see the receipt/timeout/output-contract/schema-grounding mechanics above. A malformed or missing `--schema-file` is a usage error (`EXIT_USAGE`, 3), never a silently degraded run — validation happens in `main.py` before the pipeline is called. `--json` puts the streamed model output on stderr and the receipt (pure JSON) on stdout; exit codes are 0 (ran, receipt exists — regardless of `qa_approved`/`deviation`), 2 (engine failed or timed out — still a partial receipt), 3 (usage error). Full detail on what's implemented here and what's still owed by the calling side lives in [docs/handoff-fenix-parte-b.md](docs/handoff-fenix-parte-b.md) — that doc is the handoff artifact for `docs/plan-mitigation-fenix-outsourcing-controls.md`'s Parte B (the 11 controls fenix needs to add on its own side; none of them live in this repo).
